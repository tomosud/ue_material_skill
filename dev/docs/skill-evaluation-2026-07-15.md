# ue-material スキル実装評価(2026-07-15)

対象コミット: `2c0b9fd`(main, クリーン状態)
検証環境: offline uv Python ランタイム / UE 5.8.0 ソースベースライン

この文書は開発用メモであり、配布スキル(`skills/ue-material/`)には含めない。

## 総評

**設計思想は非常に堅牢。実運用上のボトルネックは「監査カバレッジ 6/359」と
「UEソース必須の運用要件」の2点に集約される。**

MGJSON を唯一の会話表現とし、冗長な T3D・GUID・Pin レコードを決定論的な
Python スクリプトに完全に隠蔽する設計は、トークン効率と再現性の両面で正しい。
provenance(出所)をフィールド単位で分離し「ソース監査 / オフライン往復 /
Editor 実証」を混同しない証拠モデルは、AI が知識をでっち上げる典型的な失敗を
構造的に防いでいる。この日の検証時点で 26 件のオフラインテストが全て合格し、
カタログ再生成はバイト単位で決定論的である。

## 1. スキルとしての効率性(トークン・コンテキスト)

### 実測値

| 項目 | サイズ | コンテキストへの読込 |
|---|---|---|
| `SKILL.md` | 147行 / 約8KB | 起動時のみ(必須) |
| `references/*.md` 6本 | 各10〜220行 | 条件付き(タスク種別で分岐) |
| `catalog/nodes.json` | 312KB | **読込禁止** — search_catalog.py 経由 |
| `catalog/node-evidence.json` | 180KB | 同上 |
| `catalog/legacy-node-prose.json` | 66KB | 同上(検索結果に結合) |
| scripts 4本 | 計2,400行 | 読込不要(実行のみ) |

### 良い点

- **プログレッシブ・ディスクロージャが徹底されている。** SKILL.md はワークフロー
  分岐・安全規則・検索ルーティングのみ(109→147行)。Custom 式の規則は Custom を
  扱う時だけ、MF 呼び出し規則は関数呼び出し時だけ読む構造。359行の Markdown
  ノード表は撤去済みで、`nodes-index.md` は10行のエントリポイントに縮退した。
- **カタログ 608KB を一切コンテキストに載せない。** `search_catalog.py` が
  クラス名・Pin・プロパティ・ソースシンボル・レガシー和文まで横断検索し、
  1ノード=1レコード(4〜6行)で返す。全ノード分の生 JSON を読む場合と比べ
  実質 95%以上の削減。
- **T3D を会話に流さない規則が明文化されている**(「Never paste the full T3D」)。
  典型的なマテリアルグラフの T3D は数千〜数万トークンになるため、これが
  最大の効率化要因。クリップボード直結(`--to-clipboard` / `--from-clipboard`)で
  中間テキストの往復自体を消している。
- **検証・生成が LLM 推論でなくスクリプト実行。** validate → build の決定論的
  パイプラインなので、リトライによるトークン浪費が起きにくい。

### 改善余地

- **検索結果に関連度順位がない。** `search_catalog.py texture sample` は
  アルファベット順で全一致候補を返すため、本命の `TextureSample` に到達する
  前に周辺ノードを大量に読むことになる。完全一致クラス→Pin一致→本文一致の
  順で並べ替え、既定で上位 N 件に制限(`--all` で解除)するとレコード数が
  数分の一になる。
- **「使用前に必ず UE ソースを inspect せよ」が毎回のトークンコストになる。**
  正しさのための意図的なトレードオフだが、監査済みノード(現状6件)は
  ソース再読なしで使ってよい、という緩和規則を provenance に基づいて
  明文化すれば、監査が進むほど自動的に軽くなる構造にできる。

## 2. 確実さ(生成結果の信頼性)

### 良い点

- **証拠モデルが三層分離**(source audit / offline roundtrip / Editor evidence)
  されており、`verified` という曖昧な boolean を廃止済み。「ソースを読んだ」
  ことと「Editor に貼れた」ことを混同しない。検索結果にも
  `source(schema=..., description=...)` `editor(roundtrip=...)` が毎行付く。
- **フェイルセーフの規則が具体的:** Material Root は絶対に生成・接続しない/
  未知ノードは推測せず Editor サンプル(`--no-catalog --keep-pos`)を要求/
  貼り付け失敗時は投機的 T3D を繰り返し貼らずコピーバック比較、と
  失敗モードごとの回復手順が定義されている。
- **validate.py が build の前提ゲート**(936行、Custom 式の HLSL 制約・動的 Pin・
  TArray 構造まで検証)。エラーがあれば build に進めない規則が SKILL.md の
  最上位「Non-negotiable rules」にある。
- **Material Function 資産は「パスと Pin schema の実証拠がない限り推薦禁止」。**
  参照チェックアウトに `Engine/Content` が無い事実を認め、82 関数のプロース説明を
  隔離した判断は誠実で、幻覚由来の事故を最も起こしやすい領域を封じている。
- 実測: Constant2Vector/3Vector の出力 Pin 名がカタログの意味論的マスク名でなく
  ソース生成名(`Output`, `Output2`...)である誤りをソース監査で検出・修正済み。
  監査プロセスが実際に誤りを見つけている実績がある。

### 弱点・リスク

1. **監査カバレッジが 6/359(1.7%)。** schema=verified は Custom, Constant,
   Constant2Vector, Constant3Vector, Add, Multiply のみ。残り 353 ノードは
   Pin 構成すら `pending` で、説明文は `legacy_unverified` の和文レガシープロース。
   「毎回ソースを読め」という規則でカバーしているが、規則の遵守は
   モデルの自制に依存する。**確実さの実体は現状、規則 ≫ データ。**
2. **`UE_SOURCE_ROOT` が無い環境での挙動が未定義。** 配布先ユーザーが
   エンジンソースを持たない場合、「使用前にソース inspect」という
   非交渉規則が満たせない。SKILL.md にフォールバック(監査済みノード限定運用、
   もしくは Editor サンプル要求への切替)を明記すべき。
3. **Editor 実証がほぼ皆無**(検索結果は軒並み `editor(roundtrip=false)`)。
   ソース監査は貼り付け成功を保証しない、と自ら定義している以上、
   Editor 自動化ハーネス(deferred リスト記載済み)が無い限り
   「貼ったら Pin が消える」系の回帰は人力でしか検知できない。
4. **検索結果のレガシー和文説明は明示ラベル付きとはいえ、モデルが
   事実として引用する誘惑が構造的に残る。** 各レコード末尾の
   "verify node facts..." の一行注意は良いが、説明文の前に
   `[legacy/unverified]` のようなインライン接頭辞を付ける方が誤用に強い。

## 3. アップデートの方法(現状評価と提言)

### 現状の更新パイプライン(dev/docs/source-update.md)

```
UE_SOURCE_ROOT 設定
  → gen_manifest.py      (359クラス宣言をソースから再走査)
  → gen_node_evidence.py (宣言証拠を更新、audits/ の人手監査は保持)
  → catalog_merge.py     (dev/catalog/generated + audits → 配布カタログ、決定論的)
  → 差分の人手レビュー(変更クラスごとにコンストラクタ・Compile 等を確認)
  → ゲート実行(unittest 26件 / check_english / check_distribution)
```

**評価: 構造は正しい。** 生成(機械)と監査(人手 override)が分離され、
マージが決定論的なので差分レビューが機能する。宣言の証明と挙動の証明を
混同しない設計もパイプラインに反映済み。dev → skills の一方向依存と
`check_distribution.py` により、配布物が開発データを参照する事故も機械検知できる。

### ギャップと提言

1. **カタログ diff ワークフローが未実装**(deferred 項目に記載あり)。
   UE 5.8→5.9 のようなバージョンアップ時、`gen_manifest.py` の再走査で
   何百件の差分が出ても「クラス追加/Pin 変更/デフォルト変更/削除」を
   分類するツールがない。`manifest.json` の前後比較で変更種別を出力する
   `catalog_diff.py` を最優先で追加すべき。**これが無いとエンジン更新の
   たびに全件人手レビューになり、更新が事実上止まる。**
2. **配布スキルにバージョン識別子がない。** SKILL.md frontmatter か
   カタログメタデータに `skill_version` と `ue_baseline: 5.8.0` を持たせ、
   インストール済みスキルの世代を機械判別できるようにする。更新は
   「`skills/ue-material/` を丸ごと上書きコピー」が正であることも
   README に一行明記する(現状インストール手順のみで更新手順が無い)。
3. **監査の進め方はバッチ計画(Phase 4)通り使用頻度順が正しい。**
   ただし 353 件を人手で消化するのは非現実的なので、
   「安価なモデルで一次抽出 → 上位モデル/人手でソース照合承認 →
   audits/ に override 追加」という既存の swarm 方式を Phase 4 バッチにも
   適用し、承認済みだけ `verified` に昇格させる運用を推奨。
4. **ゲートの自動化(CI)が無い。** 全ゲートがローカル手動実行。
   最低限、コミットフックか GitHub Actions で
   unittest + check_english + check_distribution + catalog_merge --quiet の
   再生成差分ゼロ確認を回すと、決定論性の退行を即検知できる。
5. **Editor 回帰の自動化**(deferred 記載の import→export→parse→比較ハーネス)は
   バージョンアップ時の最終保証として重要。UE の Functional Test /
   Python Editor スクリプトで T3D 貼り付け→コピーバック→canonical MGJSON 比較を
   1コマンド化できれば、`editor-evidence.json` を機械更新できるようになる。

## 4. 結論

- **効率性: 高い。** カタログ非読込・検索一本化・T3D 非表示・条件付き参照読込の
  組み合わせで、スキル起動時の固定コストは SKILL.md 約8KBのみ。改善点は
  検索の関連度順位と、監査済みノードのソース再読免除。
- **確実さ: 設計は最高水準、データがまだ追いついていない。** 証拠三層分離と
  フェイルセーフ規則は模範的だが、実効性は監査 6/359 と Editor 実証ゼロが上限。
  当面の確実さは「毎回ソースを読む」規則の遵守に依存する。
- **アップデート: 手順は文書化済みで決定論的だが、エンジン更新に耐える
  diff 分類ツールと配布バージョン管理が欠けている。** catalog_diff の追加、
  skill_version の導入、ゲートの CI 化の3点が次の投資対象。

### 推奨着手順

1. `catalog_diff.py`(エンジン更新耐性 — 更新が止まる前に)
2. SKILL.md に `UE_SOURCE_ROOT` 不在時のフォールバック規則を追記
3. 検索の関連度順位 + 既定件数制限(トークン削減)
4. 頻出ノード上位 30〜50 件の監査バッチ(Phase 4 batch 2)
5. ゲートの CI 化、その後 Editor 自動化ハーネス
